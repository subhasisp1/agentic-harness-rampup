# DAY 3 :
Yesterday's tool call had many python codes wrapped around the llm invoke call, so in order to get the answers back to your llm,
we had to manually write the codes and tghe loops.
To tackle that we will use create_agent which will take the llm, the list of tools avaialble, and the system prompt("ake facts from the tools, and do all arithmetic
with the calculator. Do not guess numbers."). 
When invoked with an input, what comes back is a compiled LangGraph state . The whole graph now has 2 nodes, llm node and tool node.
The LLM decides wheather to execute the tool node or to pass the answer to end user.Tool calls executes the tools node and loop back with the result.

To experiment with it , I passed the prompt such that it should be using 2 different tools , one after another , and then pass the result. And the script 
sucecceded.The system prompt does real work. Without "do all arithmetic with the calculator", the model itself does the subtraction itself. That is
correct here(as the task is simple), but good excercise could be always forcing llm to pass tool calls if a tool for that task is available.

During the experiment , I came to know about streaming , which allows model to produce outputs tokens/words wise instead of all output at once.
That's how all te popular chatbots do the conversation to make it llok lively.I also traced the tools calls to see tools being called during the loop 
execution.

The 'recursion_limit' can be considered as a guardrail :if the model kept requesting tools forever, the graph stops after a fixed number of steps instead of burning
tokens.A type of harness applied around the llm.
