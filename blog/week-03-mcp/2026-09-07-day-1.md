# Week 3, Day 1 (Mon): the protocol by hand

Goal is to serve the same week-2 tools from a standalone process(which in our case is MCP ), then talk to that process with raw JSON-RPC
before any client library touches it. No model calls today.


## Concepts as takeaways:
- Understood that an MCP server is a process. The stdio transport is newline-delimited JSON-RPC(JSON-RPC messages where each 
  request or response is a single valid JSON object placed on its own line and ended with a newline character): one JSON object
  per line on stdin and stdout. stdout is the wire(anything printed there corrupts the wire), so the server must never print to it; 
  logs go to stderr.`@mcp.tool()` turns a typed function into a tool: the inputSchema in tools/list is generated from the type hints, 
  the same idea as LangChain's `@tool`.
  
  
- `initialize` (a request, has an id) -> reply with the server's capabilities and
  protocolVersion -> `notifications/initialized` (a notification, no id, gets no reply) -> only
  then tools/list and tools/call.


- `tools/list` returns names, descriptions and JSON schemas: exactly what a harness shows the
  model as tool definitions. `tools/call` returns a content list plus an `isError` flag.
  


## What went wrong or took time:
- Verified in the venv before writing code: `mcp.server.fastmcp` does not exist in SDK 2.x. The
  import error itself says FastMCP was renamed to MCPServer and links the migration guide.
- I expected an unknown tool to be a JSON-RPC protocol error (an `error` object, per spec). This
  SDK returns an `isError: true` result instead; the first run crashed on `reply["error"]` and I
  aligned the script accordingly.
