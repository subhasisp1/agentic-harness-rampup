# Week 3, Day 3 (Wed): real tools, and policy


Today's goal is to make second server with tools that can actually read/write instead of the toy tools that we were using till now, 
and a per-tool policy table instead of week 2's blanket y/n.


I prepared a sandbox folder such that requested path goes inside the sandbox folder, and 
absolute paths outside it are refused. The refusal is a returned string, not an exception:
the model reads "Refused: the path leaves the sandbox." and can explain itself, and the 
wire never sees an error.So read/write approval happens before anything goes to the model.
Also created a policy as a dict, not a conversation: `{"read_file": "auto", "write_file": "ask", ...}`
plus a default of "ask" for any tool the dict does not name. The approve node checks the
table per proposed call; only "ask" tools reach `interrupt`. The model never gets to decide before this:
nothing in the prompt mentions the policy, it lives where the model cannot argue with it.
 
One thing found during running the scripts: the model proposed calculator and write_file in a single turn;
approvals came back [True (auto), interrupt (ask)], so the run paused exactly once.


## Takeaways
- A tool is a security boundary; the policy is part of the harness, not the model.
- Refusals as data keep the loop alive: the model hears "no" the same way it hears a result.
