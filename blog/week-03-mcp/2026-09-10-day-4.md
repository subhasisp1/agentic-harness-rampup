# Week 3, Day 4 (Thu): someone else's server


Todays's goal is to pull in a server I did not write, purely by configuration, and let the policy default handle
the unknown tool(s).

## Concepts, in plain words
- The whole integration is one config entry: command `.venv-client/bin/python`, args
  `["-m", "mcp_server_fetch"]`. Toolbelt can now read web pages.
- The fetch tool's name, description and schema come from ITS server over tools/list, exactly
  like mine do. The model sees them all the same way; the origin of a tool is invisible to it.
- `fetch` is not in the POLICY table ( the one dict I prepared yesterday ), so it falls under DEFAULT_ACTION = "ask". 
  For a  third-party server the approval policy is default-deny, so it is restricted automatically rather than after 
  I write rules for it.
- The adapters open a fresh session per tool call (stateless): each fetch spawns the server
  process, calls, and closes. Fine here; a server with in-memory state would need the
  session-reuse mode instead. Ours keep state on disk (sandbox/, notes.txt), so nothing is lost.

## Takeaways
- Everything about a tool the model sees is self-reported by its server. The policy table is
  the harness's own opinion, and the only one that decides.
