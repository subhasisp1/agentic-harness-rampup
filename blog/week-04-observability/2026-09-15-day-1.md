## Goal
So far the harness prints a final answer and nothing else.Weeks 1 to 3 built the four primitives the program set out with: prompt the model, 
let it call tools in a loop, give it memory, constrain it. The result works when I watch it work, and that
is the whole problem. I cannot say what a turn costs, I cannot prove a prompt change did not
break the notes question, and when the router misclassifies a question I only notice by reading
the output.

The current harness makes two model calls per turn, runs a tool loop, and since week 3 its tools write files and 
fetch the web. An unmeasured harness with real tools is a liability, and every serious harness carries this layer: traces,
cost accounting, and a regression suite. This week builds it the way the earlier weeks built the
loop and the tool boundary, by hand first, then landing on the standard.



## Concepts takeaways :
- A callback handler is an object you hand to LangChain that it calls back at fixed moments during a run.
  You subclass BaseCallbackHandler and override only the moments you care about: on_chain_start/end, 
  on_chat_model_start, on_llm_end, on_tool_start/end, plus the error variants.You pass an instance in the config, {"callbacks": [tracer]}.
  LangChain then calls those methods as it runs, handing each one a run_id and a parent_run_id.
- A span is one start and end pair. It needs four things: a name, an id, its parent's id, and
  the two timestamps. `run_id` and `parent_run_id` come with every event, and those two fields
  alone rebuild the whole tree.
