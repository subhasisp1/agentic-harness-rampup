# INTERRUPT :

`interrupt(value)` from `langgraph.types` is a function you call inside a node. The graph stops, the checkpointer saves the state, and `invoke()`
returns the state with one extra key, `__interrupt__`, a list with one `Interrupt` whose `.value` is what the node passed in. While paused,
`graph.get_state(config).next` is `('tools',)`. To resume : `graph.invoke(Command(resume=answer), config)`. The node runs again from its first
line, and this time `interrupt()` returns the answer instead of stopping.

That last part matters. The node re-runs from the top, so anything before an interrupt runs on every resume. With two proposed tool calls the node
was entered three times. So the tool node collects all the approvals first ( one interrupt per proposed call, one pause each ) and only then runs
the tools, once .

```python
def run_tools(state: State) -> State:
    calls = state["messages"][-1].tool_calls
    approved = [interrupt({"tool": c["name"], "args": c["args"]}) for c in calls]
    results = []
    for call, ok in zip(calls, approved, strict=True):
        if ok:
            output = TOOLS[call["name"]].invoke(call["args"])
        else:
            output = "Rejected by the user; not run."
        results.append(ToolMessage(content=output, tool_call_id=call["id"]))
    ran = sum(1 for ok in approved if ok)
    return {"messages": results, "tool_calls_made": state["tool_calls_made"] + ran}
```

A rejected call still gets a `ToolMessage`. The API wants a result for every tool call ; the model reads the rejection and answers with what it has.
The pause needs a checkpointer, because the pause is a saved checkpoint and `thread_id` says which conversation to resume. Same `InMemorySaver` and
`{"configurable": {"thread_id": ...}}` as week 1.

The script mentioned above is a small loop : invoke, and while the result has `__interrupt__`, print the proposal ( `Run calculator(expression='31 - (21 + 8)')? [y/n]` ),
read y/n, and invoke again with `Command(resume=True/False)`.


# THINGS THAT TOOK TIME :
- Sending new input to a paused thread does not resume it. LangGraph starts a new run and leaves the earlier tool call without a result. Today's
  script cannot hit this ( one question, approvals inline ), tomorrow's CLI has to handle it.


# TAKEAWAYS :
- The pause is a checkpoint ; the resume is the same node run again with the answer filled in.
- Approval enters the graph as data ( True or False ) and leaves it as a ToolMessage.
